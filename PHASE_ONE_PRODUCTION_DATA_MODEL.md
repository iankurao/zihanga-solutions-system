# BSF Production Chain — Canonical Phase One Data Model

## Purpose and scope

This document defines a proposed relational source of truth for the Phase One
production chain:

```text
Farm → Waste Source → Collection Run → Waste Lot
     → Substrate Batch → Production Batch → Production Events
     → Harvest → Drying Batch → QC → Product Lot → Inventory
```

It uses the useful concepts in `backend/migrations/erp_schema_v2.sql`, while
accounting for the live application schema described in
`PRODUCTION_CHAIN_CURRENT_STATE.md`. This is a design only. It does not assert
that the ERP SQL has been applied to a live database; the current-state analysis
did not verify the live schema.

Phase One is intended to establish traceable production lineage and stock
accounting, not redesign the whole application. Existing farmer, sales,
hatchery, and fly-facility features remain adjacent unless specifically linked
below.

## Canonical modeling rules

1. **Use database keys for relationships.** Each entity has a surrogate primary
   key. Human-readable codes are unique business references, never substitute
   foreign keys.
2. **Use line/input tables for many-to-many relationships.** Do not put lists
   of source lots, trays, substrate batches, or other IDs in text columns.
3. **Use PostgreSQL types consistently.** Recommended new keys are
   `BIGINT GENERATED BY DEFAULT AS IDENTITY`; quantities are
   `NUMERIC(14,3)`; timestamps are `TIMESTAMPTZ`. Existing IDs may be preserved
   during a migration, but every referencing column must use a compatible type.
4. **Make units explicit.** Quantity columns are paired with a constrained
   `unit_code` (or a foreign key to a small shared units table). Use `kg` as the
   canonical mass unit and convert legacy gram values during migration only
   when their meaning is known. Percentages and measurements such as temperature
   have named units and are not mass quantities.
5. **Separate occurrence from recording.** Operational records use
   `occurred_at` (or a more specific event timestamp) and `created_at`; mutable
   master/batch rows also use `updated_at`. Store timestamps in UTC.
6. **Use user foreign keys for actors.** `created_by_user_id`,
   `recorded_by_user_id`, `approved_by_user_id`, and similar fields reference
   `users.user_id`. Do not use a username or display name as the actor key.
7. **Scope operations to a farm and, when physical, a facility.** A facility is
   a farm's operating site. Its `farm_id` must agree with the owning farm on
   any row that stores both. Child rows may inherit scope through their parent;
   do not duplicate farm/facility fields on every junction row. Where both IDs
   are stored, use a composite foreign key or equivalent database constraint
   so a row cannot pair a facility with a different farm.
8. **Keep status vocabularies controlled per entity.** Use documented
   `CHECK` constraints or lookup tables, not free-form text or a single status
   vocabulary shared by unrelated processes.
9. **Keep stock out of product-lot snapshots.** Posted inventory movements are
   the stock ledger. Available quantity is calculated from ledger entries, not
   stored as a separately edited copy.
10. **Do not duplicate measurements.** A specialized event owns its detailed
    measurements. A generic parent event may leave its optional quantity empty
    when its child already records the relevant quantity.

## Scope entities

The current schema does not define a farm or facility master suitable for this
chain. Add these roots rather than treating `farmer_profiles` or free-text
facility/tray labels as farm records.

| Entity | Primary key | Business/reference ID | Important relationships | Status, quantities, time, actor, scope |
|---|---|---|---|---|
| `farms` | `farm_id` | `farm_code`, unique | None | `status` (active/inactive); no quantity; `created_at`, `updated_at`; creator user; top-level scope. Represents the operating/owning farm, not a farmer login. |
| `facilities` | `facility_id` | `facility_code`, unique within farm | `farm_id → farms` | `status`; no quantity; timestamps and creator; farm scope. Represents a named site/facility. |

## Canonical production-chain entities

For compactness, `created_at` and actor below mean the common audit fields in
the modeling rules. “Scope” identifies the farm/facility reference stored on
the row or inherited from its parent. Optional quantities are nullable only
when the process does not measure that quantity.

### Production events and harvest

`production_events` is the common event envelope. Domain tables below have a
one-to-one relationship to it (`production_event_id` is both the child primary
key and a foreign key). Event time, actor, batch, status, and scope come from
the envelope rather than being repeated inconsistently in each child.

| Entity | Primary key | Business/reference ID | Important foreign keys | Status and quantity/unit | Timestamps, actor, scope |
|---|---|---|---|---|---|
| `production_events` | `production_event_id` | `event_code`, unique within farm | `production_batch_id → production_batches`; `farm_id → farms`; `facility_id → facilities`; optional parent event for corrections/reversals | `status` (recorded/voided); optional single summary quantity and unit; controlled event types include feeding, monitoring, health, and harvest | `occurred_at`, `created_at`; `created_by_user_id` and optional `voided_by_user_id`; farm/facility. Append events; correct by an auditable reversal/amendment, not silent overwrite. |
| `feeding_events` | `production_event_id` | Inherits `event_code` | PK/FK → `production_events` | Feed type; amount offered and amount consumed, each with unit (`kg`); optional larvae biomass and unit. Do not overload one generic quantity for distinct values. | Inherits event timestamps/actor/scope. |
| `monitoring_events` | `production_event_id` | Inherits `event_code` | PK/FK → `production_events` | Monitoring type and typed readings, e.g. temperature °C, relative humidity %, ammonia ppm; optional reading units for extensible measurements; no fabricated mass quantity | Inherits event timestamps/actor/scope. Store a timestamped observation, not just a tray label. |
| `health_events` | `production_event_id` | Inherits `event_code` | PK/FK → `production_events` | `status` (open/follow_up/resolved/closed); issue, severity, action, and follow-up; quantity/unit normally not applicable | Inherits event timestamps/actor/scope; include `resolved_at` and resolution actor when resolved. |
| `harvests` | `harvest_id` | `harvest_code`, unique | `production_event_id → production_events` (unique); production batch is obtained from that event | Wet weight and explicit unit (`kg` or `g`); harvest stage | Harvest `occurred_at`, operator, location, and notes are recorded with the event; farm/facility inherited from its batch. One production batch can have multiple harvests. |

## Relationships and integrity expectations

```text
farms
 ├─ facilities
 ├─ waste_sources
 └─ waste_collection_runs ── waste_collection_items ── waste_lots
                                                    └── substrate_batch_inputs
substrate_batches ── substrate_batch_inputs
       └──────────── production_batch_inputs ── production_batches
                                                ├─ production_batch_units ── production_units
                                                └─ production_events
                                                   ├─ feeding_events
                                                   ├─ monitoring_events
                                                   ├─ health_events
                                                   └─ harvests ── drying_inputs ── drying_batches
                                                                           └──── drying_outputs
quality_checks ── quality_approvals ── product_lots ── inventory_movements
                                          ↑  ↑               ↑
                                  drying_outputs products   inventory_locations
```

The drawing groups relationships for readability; the actual foreign keys are
the ones in the entity tables above. In particular:

- Each collection item belongs to one run and one source. Its accepted material
  is represented by one or more waste lots.
- Substrate and production input tables record the actual quantity consumed or
  issued from each upstream batch/lot. They are not arrays of IDs.
- A production event always belongs to one production batch. Each specialized
  feeding, monitoring, health, or harvest row has exactly one parent event.
- A harvest event may be recorded only while its batch is `READY_FOR_HARVEST`.
  Its batch must have an explicit `harvest_limit_kg`; the sum of recorded wet
  harvests (converted to kg) cannot exceed that limit. The limit is not a
  forecast, and reaching it is not required to close harvesting.
- Marking a batch `HARVESTED` requires at least one recorded harvest event.
  Partial harvests remain separate events on the same batch; no single-harvest
  assumption is made. This implementation defines no exception to the gate.
- A drying batch consumes one or more harvest quantities through `drying_inputs`.
  Product output and inventory lots are not inferred from a matching text code.
- A product lot originates from a drying output, is associated with the product
  catalog, and cites its release approval. The release transaction must verify
  that the approval is for a passing check on the relevant drying batch.
- Posted movements form the quantity ledger per product lot and location.
  Available quantity is the sum of posted inbound quantities less posted
  outbound quantities; transfers debit one location and credit another.
- Use delete restrictions for production history. Correct or cancel records
  with statuses and auditable reversals instead of cascading deletes.

## Existing table disposition

“Reuse” below means retain the concept and, where appropriate, preserve IDs or
codes during a planned migration. It does not mean that the existing schema is
already canonical or safe to use unchanged. Legacy tables should not be dropped
as part of this design; map and reconcile their records first.

| Existing table/model | Proposed disposition | Mapping notes and limits |
|---|---|---|
| ERP `waste_sources` | **Reuse and migrate** as `waste_sources` | Keep its source-code/contact concept; add farm scope and actor FK; replace free-text waste-type lists with structured source/material data if needed. |
| ERP `waste_collection_runs` | **Reuse and migrate** as `waste_collection_runs` | Keep run code and route/vehicle details; add farm/facility FKs and timestamps/actor FKs. Remove `planned_sources` text list. Run total should reconcile to its item rows. |
| ERP `waste_collection_items` | **Reuse and migrate** as `waste_collection_items` | Keep source/run relation and lot code as a source for migration. Separate the collected item from accepted `waste_lots`; add consistent item status and actors. |
| ERP `substrate_batches` | **Reuse and migrate** as `substrate_batches` | Keep batch code, preparation and quality measurements. Replace `waste_lot_ids TEXT` with `substrate_batch_inputs`; remove or reconcile duplicate approval fields through quality checks/approvals. |
| ERP `production_batches` | **Reuse and migrate** as `production_batches` | Keep batch code, stage dates, and operational status where meaningful. Replace `substrate_batch_id` with `production_batch_inputs` for explicit, measured inputs; replace `tray_ids TEXT` with unit and allocation relations; do not use the batch row as the sole harvest record. |
| ERP `lifecycle_events` | **Migrate into** `production_events` | Preserve event date/type/stage details and resolve actor names to users. Extend it as the common parent for specialized event rows. |
| ERP `product_lots` | **Reuse and migrate** as `product_lots` | Preserve lot codes/quality/date details. Add `products`, `drying_output_id`, and release approval linkage. | Operational `waste_sourcing` | **Migrate and retire as write target** | Some rows can become source/run/item/lot records after source deduplication and explicit acceptance mapping. A row's `source_name` is not automatically a stable supplier identity; do not invent a source match. |
| Operational `storage_records` | **Keep as legacy history or migrate only when reconcilable** | No waste-lot FK exists. Do not attach a storage observation to a guessed lot. If storage tracking is required in Phase One, define a lot-linked storage-event relation before migrating those records. |
| Operational `processing_records` | **Keep as legacy history or migrate only when reconcilable** | It has no input/output links or clear unit for `waste_reduction`. Do not infer substrate inputs/outputs. Define processing semantics separately if it is to become a first-class transformation. |

| Operational `feeding_schedule` | **Migrate** to `production_events` + `feeding_events` | Resolve `tray_batch_id` to a production batch/unit before linking. Map each weight/quantity with its intended meaning and unit; do not assume a unitless column is kg or grams. |
| Operational `environmental_monitoring_larvaefeeding` | **Migrate when resolvable** to `production_events` + `monitoring_events` | Its `tray_facility_id` is text, not a production FK. | Operational `health_intervention` | **Migrate when resolvable** to `production_events` + `health_events` | Resolve free-text `tray_batch_id`; map resolution values and timestamps explicitly. |
| Operational `harvest_yield` | **Migrate when resolvable** to `production_events` + `harvests` | Resolve `tray_batch_id`; establish the intended unit for `larvae_collected` and the meaning of `processing_method`. Do not also copy the quantity into a production-batch summary. |
| Operational `drying_batches` | **Migrate** to `drying_batches` | Preserve batch code/date/method/status/personnel evidence; replace text child references with `drying_batch_id` foreign keys and user references where identities resolve. |
| Operational `drying_input` | **Migrate when harvest can be identified** to `drying_inputs` | `batch_id` is text and does not identify a harvest. Map measured input quantities; `dried_by_personnel_kg` is ambiguous and must not be auto-mapped. |
| Operational `drying_output` | **Migrate** to `drying_outputs` | Preserve measured output and notes. Retain `actual_ratio`/`yield_percentage` only as historical values until numerator, denominator, and moisture basis are defined; new yields should be calculated from measured input/output. |
| Operational `drying_quality_control` | **Migrate** to `quality_checks` | Preserve inspection results and inspector text. Define controlled measurements/units, and resolve inspector to a user where possible. QC becomes a release gate only under the approval workflow. |
| Operational `drying_review_approval` | **Migrate** to `quality_approvals` | Preserve each decision and reviewer. Normalize decision vocabulary; associate it with an explicit check rather than only a free-text drying batch code. |
| Existing `users` | **Reuse** for actors | Reference `users.user_id`. Backfill old `recorded_by` values by matching usernames; unmatched names remain an explicit migration exception, not a fabricated user FK. |
| ERP `farmer_profiles` | **Do not use as** `farms` | A farmer/person profile is not the operational farm/site master. Add `farms` and relate people or profiles separately if a future workflow requires it. |
| ERP `traceability_nodes` / `traceability_edges` | **Do not use as** the Phase One lineage source of truth | Their polymorphic IDs do not enforce foreign keys. Direct relational links above are sufficient and avoid maintaining two graphs. |
| ERP `farmer_orders` and operational sales/deliveries | **Keep adjacent; integrate later** | Orders may continue to reference product lots where that schema is active. Sales/dispatch should reduce stock only through posted inventory movements; existing order rows alone do not do so. |
| Migration-era alternate feeding/drying/facility tables | **Audit as legacy; do not select as canonical** | The analysis finds conflicting names, units, ID types, and destructive SQL. Do not run them as-is; identify which records exist in the actual database before any migration. |

## Migration and cutover cautions

- The repository analysis describes tables in source files; it does not confirm
  the deployed database's applied migrations or data. Inspect the actual target
  schema and take a backup before writing a migration plan.
- Do not execute the historical `DROP TABLE`/recreate scripts as a shortcut.
  The analysis found MySQL-specific syntax in migration files while the app uses
  PostgreSQL.
- Build explicit old-to-new ID maps and preserve legacy codes. Validate row
  counts, foreign-key coverage, quantity totals, and orphan/unresolved records
  before changing application write paths.
- Do not manufacture lineage from matching labels alone. In particular, resolve
  source names, tray/batch labels, drying text IDs, and actor names from
  auditable evidence. Store unresolved rows in a migration exception report or
  retain them in the legacy table.
- This document does not define the operational UI/API rollout, exact status
  transition matrix, waste-storage event schema, processing transformation
  schema, product packaging rules, or sales reservation behavior. Resolve these
  business rules before implementation where they affect acceptance or stock.

## Repository implementation update — Step 9 Product Lot release

The implemented release slice links each newly created Product Lot to one
canonical Drying Output and to the approval that released its output-specific
passing QC check. It stores the inherited farm, product type, kg quantity,
production date, optional storage location, lot number, and generated unique
business ID. The legacy table's existing product-type field is retained rather
than introducing a product catalog as part of this release.

Availability is gated by completed drying, a passed output-specific check, and
the latest approved decision. Product-lot detail follows existing relations
upstream through the Drying Batch, Harvest, Production Batch, Substrate Batch,
and Waste Lot. Historical lots are not linked by inference. Inventory movements,
stock balance, and sales reservation/posting remain deferred; this
implementation does not claim that a Product Lot alone is an inventory ledger.
